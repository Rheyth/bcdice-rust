## 修正済み（Rustを直した不一致）

### 1. 空白のみ・空文字の入力で `eval` が例外にならなかった

| | |
|---|---|
| 入力 | `""` / `" "` / `"   "` / `"\t"` / `"\n"`（計5件） |
| 期待(Ruby) | 例外 `NoMethodError: undefined method 'gsub' for nil:NilClass`（`error: "Other"`） |
| 実際(Rust) | 例外なし・`eval` が nil 相当（`nil_result: true`, `error: null`） |
| 原因 | Ruby `Preprocessor#trim_after_whitespace` は `@text.strip.split(/\s/, 2).first` なので、`strip` 結果が空だと `nil` を返す。続く `replace_parentheses` の `nil.gsub` が `NoMethodError` を送出する（lib/bcdice/preprocessor.rb:37,45）。Rust側の `preprocessor::process` は同じ入力で空文字を返す実装になっていた。 |
| 対応 | `preprocessor::is_blank()` を追加し、`eval::eval_input` が前処理より前に `EvalError::BlankInput` を返すようにした（rust/src/preprocessor.rs, rust/src/eval.rs）。`Base#eval` が「nil を返す」のか「例外になる」のかは呼び出し側から観測できる差なので、本家の未定義動作でも `Err` として再現する方を採った。 |
| 検証 | `eval::tests::blank_input_is_an_error_like_ruby` / `preprocessor::tests::is_blank_matches_ruby_trim_after_whitespace`。TOMLハーネス 327/327 に影響なし（`test/data/*.toml` に空白のみの入力は存在しない）。 |

U+3000（全角空白）は Ruby の `String#strip` にも正規表現 `\s` にも含まれないため
この扱いの対象外で、`"　"` 単独は両側とも nil のまま一致する。

> add_dice / randomizer / game_system 等）を `crate::Int`（num-bigint ラッパ）へ一斉移行し、

**推定原因（特定済み）**

- Ruby の `Integer` は多倍長なので桁が伸びる。
- Rust移植は数値を `i64` 固定で持つ。
  - 字句解析: `rust/src/lexer.rs:137` — `literal.parse::<i64>().unwrap_or(i64::MAX)`。
    `i64` に収まらない**リテラル自体**が `i64::MAX` に潰れる。式のエコー表示にも出る
    （`C9223372036854775808` → `c(9223372036854775807)`、`2D6>=99999999999999999999`
    → `(2D6>=9223372036854775807)`）。
  - 算術: `rust/src/arithmetic.rs:31-33,150` — `saturating_add` / `saturating_sub` /
    `saturating_mul`。**桁溢れは飽和**する（ラップしない）。
- 乖離の境界は明確で、**中間値・最終値・リテラルのいずれかが `i64` の範囲外に出た時のみ**。
  範囲内であれば全件一致する（`bignum` 群 23件中 12件は一致）。
  `C1000000000*1000000000`（1e18）や `C4611686018427387903*2`（2^63-2）は一致し、
  `C4611686018427387904*2`（2^63）から乖離する。
- 飽和演算なので **debug ビルドでも release ビルドでも結果は同一**
  （ラップやオーバーフローパニックは起きない）。2570件を両モードで実行して
  JSONL がバイト単位で一致することを確認済み。

**修正しなかった理由**

多倍長整数への移行は `lexer` / `arithmetic` / `add_dice` / `randomizer` /
`game_system`（`check_result`）など数値を扱う全経路に波及し、`i64` を使っている
既存の公開API（`CmpOp::compare`、`RandResult`、`Randomizer` の各メソッド等）の
シグネチャ変更を伴う。本タスクの制約「既存の `rust/src/*.rs` の公開APIを壊さないこと」に
抵触し、かつ TOML 327ケースの回帰リスクがある。P5 は差分ファズの運用基盤構築が範囲なので、
**検出・特定まで**を成果とし、修正は別フェーズへ送る。

**将来の修正方針**

`i128` への引き上げは境界を押し広げるだけで解消にはならない（Rubyは無制限）。
`num-bigint` 相当の多倍長型を導入し、数値経路の型を一斉に差し替えるのが本筋。
その際 `bignum` 群 23件が回帰テストとして機能する。

## Rubyの非決定性について

差分ファズで観測された非決定性は**なし**。
`bin/fuzz_runner.rb` の `LineupRandomizer` と Rust の `bcdice::randomizer::LineupSource` は
同一式（面数ごとに独立な MINSTD 乗算合同法 `state = (state * 48271) % 2147483647`、
`value = (state % sides) + 1`）で、入力1件ごとに状態をリセットする。
2609件で消費した出目の `rands` 列は全件一致しており、出力差分は乱数差異ではなく
ロジック差異だけを反映している。

例外時に出目が残るケース（`x100 101D100` → `TooManyRands` かつ出目 9999 個、
`x100 200D100` → 同 10000 個）でも `rands` 列が完全一致することを確認済み。
これは「エラーでも消費済みの出目を返す」規約（Rust側 `eval::EvalOutcome#rands`）が
実際に効いていることの実証にあたる。
